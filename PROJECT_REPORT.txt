4. BACKEND DETAILS
--------------------------------------------------------------------------------
ENTRY & SERVER LIFECYCLE (src/server.js)
--------------------------------------------------------------
1. Connects to MongoDB via connectDatabase() - server does NOT listen until DB
   is reachable.
2. Creates Express app via createApp().
3. Listens on configured PORT (default 5000).
4. Initializes Socket.IO on the same HTTP server (shared CORS origins).
5. Graceful shutdown on SIGINT/SIGTERM: closes Socket.IO -> HTTP server ->
   MongoDB.

ENVIRONMENT (src/config/env.js)
--------------------------------------------------------------
Validated with Zod:
  NODE_ENV, PORT, MONGODB_URI, CLIENT_URL
  JWT_ACCESS_SECRET / JWT_REFRESH_SECRET (min 32 chars, must differ)

DATABASE (src/config/db.js)
--------------------------------------------------------------

- serverSelectionTimeoutMS: 10_000
- Connection-state logging; secrets redacted from error messages

--------------------------------------------------------------

- JWT access token (short-lived) + refresh token (HttpOnly cookie)

- Department-scoped HOD/tutor authorization
- Rate limiting, helmet headers, CORS origin whitelist
- File upload size limits (5 MB max for documents)

6. AUTHENTICATION FLOW
--------------------------------------------------------------------------------
LOGIN
--------------------------------------------------------------
1. User submits email + password on a role-specific login page
   (/login/hod, /login/tutor, /login/parent, /admin/login).
2. Frontend calls POST /api/v1/auth/login.
3. Backend validates credentials, returns:
   - accessToken (JWT, in response body)
   - refreshToken (set as HttpOnly cookie)
   - user object (role, department, etc.)
4. Frontend stores the access token in memory and the user in
   localStorage/sessionStorage.
5. Socket.IO connection is established with the token for real-time
   notifications.

TOKEN REFRESH
--------------------------------------------------------------
- On app load, AuthProvider calls POST /api/v1/auth/refresh using the refresh
  cookie to silently restore the session.
- API client (apiClient.js) has an interceptors chain: on 401, it retries
  with a refreshed access token; if refresh fails, it logs the user out.

LOGOUT
--------------------------------------------------------------
- Calls POST /api/v1/auth/logout, clears the refresh cookie, removes
  token/user from storage, disconnects Socket.IO.

PASSWORD CHANGE
--------------------------------------------------------------
- POST /api/v1/auth/change-password validates current password, hashes the
  new one, issues a new access token.

ROUTE PROTECTION
--------------------------------------------------------------
- Frontend ProtectedRoute checks user.role against the required route role.
- Backend middleware enforces role/department authorization on every mutating
  endpoint.

7. LEAVE WORKFLOW
--------------------------------------------------------------------------------
1. SUBMIT: Parent logs in, selects a linked child, fills leave type, date
   range, reason, optional document (<=5 MB). Submits -> status pending.
2. NOTIFY: HOD of the student's department receives a new_application
   notification (Socket.IO + in-app).
3. DECIDE: HOD reviews in /hod/leave-requests:
   - Approve (with optional remarks) -> status approved, tutor of the
     student's class notified, parent notified.
   - Reject (mandatory reason >=15 chars) -> status rejected, parent
     notified, tutor NEVER notified.
   - Reopen (mandatory reason >=15 chars) -> status reopened, prior
     decision preserved in history, parent notified to correct and
     resubmit.
4. TUTOR: Sees only approved leaves for their assigned classes in
   /tutor/approved-leaves.
5. ADMIN: Read-only oversight of all leave requests and department reports.

8. FRONTEND-BACKEND INTEGRATION
--------------------------------------------------------------------------------
frontend/src/context/DataProvider.jsx:
- Detects backend auth via user.isBackend || getAccessToken().
- Backend mode: Calls REST API for all CRUD and leave operations, refreshes
  local cache after each mutation.
- Demo mode: Falls back to demoStore.js (localStorage) with seeded mock data
  and relationship validation.
- Socket listeners (onNewNotification, onNotificationRead) push real-time
  updates into the local cache.

API Client (frontend/src/services/api/client.js):
- Axios instance with baseURL from VITE_API_URL (empty -> Vite proxy to
  localhost:5000).
- withCredentials: true (sends refresh cookie).
- Automatic Bearer header injection from in-memory access token.
- 401 intercept -> refresh token -> retry queue.

9. RUNNING LOCALLY
--------------------------------------------------------------------------------
PREREQUISITES
--------------------------------------------------------------
- Node.js 18+ (v24 installed)
- Docker (for MongoDB)

ONE-TIME SETUP
--------------------------------------------------------------
  # 1. Start MongoDB
  docker run -d --name clms-mongo -p 27017:27017 \
    -v clms_mongo_data:/data/db mongo:7

  # 2. Install dependencies (already done in this repo)
  cd backend && npm install
  cd ../frontend && npm install

START (two terminals)
--------------------------------------------------------------
  # Terminal 1 - Backend
  cd backend && npm run dev      # http://localhost:5000

  # Terminal 2 - Frontend
  cd frontend && npm run dev     # http://localhost:5173

SEED THE DATABASE
--------------------------------------------------------------
  cd backend
  npm run seed:admin
  npm run seed:departments
  npm run seed:phase4

USEFUL COMMANDS
--------------------------------------------------------------
  Command          Location   Purpose
  ---------------- ---------- -------------------------------------------
  npm run dev      backend   Start API + Socket.IO (nodemon)
  npm run dev      frontend  Start Vite dev server
  npm test         backend   Run test suite (needs MONGODB_URI_TEST)
  npm run lint     frontend  ESLint
  npm run build    frontend  Production build to dist
  npm run seed:... backend   Bootstrap admin / seed demo data

11. KNOWN LIMITATIONS
--------------------------------------------------------------------------------
- No production backend deployed; this is the local dev backend.
- Browser storage is not secure or shared between users.
- Uploaded documents are local metadata only (no external storage configured
  by default).
- Approved-letter PDFs are demonstration documents.
- A production deployment must: hash passwords server-side (already done),
  enforce role/department rules server-side (done), store files securely,
  keep secrets out of client code, and use HTTPS.

12. EXTENDING / ADDING USERS
--------------------------------------------------------------------------------
Via Admin UI:
  Log in as admin at /admin/login, then use /admin/hods, /admin/tutors,
  /admin/students, /admin/parents to create accounts.

Via API:
  Authenticated admin calls POST /api/v1/hods, /api/v1/tutors,
  /api/v1/students, /api/v1/parents with a Bearer token.

Via script:
  Write a Node script using the backend User model so passwords are
  bcrypt-hashed (never insert raw via mongosh, or logins will fail).
